# 模块化单体而非微服务

## 背景

功能面持续扩大（投稿、媒体、评论、互动、通知、审核、字幕、配额），需要决定架构形态：一步到位拆分微服务，还是保持单体并约束内部边界。

## 决策

模块化单体：按业务纵向切分 `internal/modules/*`（repository / service / handler 三层 + HTTPPort 协议端口），模块生产代码禁止反向依赖 core，由架构守卫测试（`TestModulesDoNotImportCoreLayers`）强制；跨模块协作经事件总线与消费方自定义接口；所有迁移以「行为保持 + 目标验证 + 分批交付」完成（A2 系列已提取 notifications / comments / interactions / moderation 四模块与事件总线）。

## 被拒替代方案

- 一步到位微服务：没有负载证据，部署、链路追踪、分布式事务与观测成本与单机部署目标冲突；
- 无边界单体（仅分层）：模块边界会随功能增长漂移——通知写路径曾出现三份镜像 INSERT 的实证代价。

## 回退条件

出现以下信号时按 roadmap 中期项分阶段拆分：媒体转码与 API 争抢资源导致 API P95 明显抬升、需要独立扩缩容、多实例写入需求成立。拆分顺序为「存储接口缝 → 转码 worker 出进程 → PostgreSQL」，每步保持单体仍可运行、可回退。
